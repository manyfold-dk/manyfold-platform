## Status

Accepted

## Context

The Manyfold Platform requires consistent naming conventions across:
- Microservices and applications
- Kubernetes resources (deployments, services, pods, namespaces)
- Container images
- Maven artifacts
- Git branches
- API endpoints

Without clear standards, naming becomes inconsistent, making resources harder to discover, troubleshoot, and manage across tools (kubectl, monitoring, logging, GitOps).

### Key Considerations

1. **Kubernetes Compatibility**: Names must follow RFC 1123/1035 DNS standards
2. **Human Readability**: Developers should quickly understand resource purpose
3. **Tooling Integration**: Names should work well with CI/CD, GitOps, and monitoring
4. **Multi-environment Support**: Clear distinction between dev, test, and production
5. **Consistency**: Predictable patterns across all resources
6. **Discoverability**: Easy to find and correlate resources

## Decision

We will adopt the following resource naming conventions for the Manyfold Platform.

### General Principles

**Lowercase-First Rule**: All resource names, identifiers, and labels MUST use lowercase letters unless explicitly required by an external standard or specification.

- **Default**: Always use lowercase (e.g., `web-frontend`, `user-service`, `prod-api`)
- **Exceptions**: Only use uppercase when mandated by:
  - Java class names (PascalCase per Java conventions)
  - Environment variables (UPPER_SNAKE_CASE per POSIX standards)
  - Constants in code (UPPER_SNAKE_CASE per language conventions)
  - Acronyms in documentation when referring to the actual standard (e.g., "REST API", "HTTP")

**Rationale**:
- Kubernetes DNS requires lowercase (RFC 1123)
- Unix/Linux systems are case-sensitive and lowercase is conventional
- Lowercase reduces cognitive load and prevents case-related bugs
- Consistent with cloud-native ecosystem conventions (Docker, Helm, etc.)

### 1. Application/Service Naming

**Format**: `{domain}-{service}`

- **MUST** use lowercase letters, numbers, and hyphens only
- **NO** uppercase letters, underscores, or special characters
- Maximum 63 characters (Kubernetes label limit)
- Should clearly indicate business domain and service purpose

**Examples**:
- `web-frontend` - Public website frontend
- `api-gateway` - API gateway service
- `user-service` - User management microservice
- `notification-worker` - Background notification processor

**Reserved Prefixes**:
- `platform-*` - Platform infrastructure services
- `monitoring-*` - Observability stack components
- `internal-*` - Internal-only services

### 2. Kubernetes Resource Naming

#### Namespaces

**Format**: `{environment}-{domain}`

**Examples**:
- `prod-web` - Production web application
- `dev-api` - Development API services
- `test-users` - Test environment for user services
- `platform-infra` - Platform infrastructure components

**Reserved Namespaces** (avoid):
- `default`
- `kube-system`
- `kube-public`
- `kube-node-lease`

**Rationale**: Environment in namespace name allows identical manifests to be deployed across environments using namespace-scoped resources.

#### Deployments, StatefulSets, DaemonSets

**Format**: `{service-name}`

The environment is captured by namespace, not resource name.

**Examples**:
- Deployment in `prod-web` namespace: `frontend`
- StatefulSet in `prod-data` namespace: `postgres`

**Rationale**: Keeps resource names environment-agnostic, enabling Helm/Kustomize reusability.

#### Services (Kubernetes)

**Format**: `{service-name}-svc` or just `{service-name}`

**Examples**:
- `frontend-svc` or `frontend`
- `api-gateway-svc` or `api-gateway`

**Recommendation**: Use `-svc` suffix when it improves clarity in kubectl output.

#### Pods

Pod names are auto-generated by Kubernetes controllers (Deployment, StatefulSet, etc.) and follow the pattern:
`{deployment-name}-{replica-set-hash}-{random-suffix}`

**Do not manually name pods** - let Kubernetes generate names.

#### ConfigMaps and Secrets

**Format**: `{service-name}-{purpose}` or `{service-name}-config` / `{service-name}-secret`

**Examples**:
- `frontend-config`
- `api-gateway-secret`
- `postgres-tls-secret`
- `app-env-config`
- `db-credentials`

**Rationale**: Clear association with the service that uses them.

### 3. Kubernetes Labels

**Standard Labels** (following Kubernetes recommendations):

```yaml
metadata:
  labels:
    app.kubernetes.io/name: user-service
    app.kubernetes.io/version: "x.y.z"
    app.kubernetes.io/component: backend
    app.kubernetes.io/part-of: manyfold-platform
    app.kubernetes.io/managed-by: argocd
    app.kubernetes.io/instance: user-service-prod
    manyfold.dk/team: platform
    manyfold.dk/environment: production
```

**Custom Label Prefix**: `manyfold.dk/`

**Standard Custom Labels**:
- `manyfold.dk/team` - Owning team
- `manyfold.dk/environment` - Environment (dev, test, prod)
- `manyfold.dk/tier` - Service tier (frontend, backend, database)

**Rationale**: Following Kubernetes recommended labels enables better tooling integration and prevents label collision.

### 4. Container Image Naming

**Image Name Format**: `{registry}/{organization}/{service-name}`

**Examples**:
- `ghcr.io/manyfold/web-frontend`
- `ghcr.io/manyfold/user-service`

**Image Tag Strategy**:

1. **Semantic version tag** (immutable): `x.y.z`
2. **Git commit SHA** (immutable): `sha-a1b2c3d`
3. **Environment-specific tags** (mutable): `latest`, `dev`, `staging`, `prod`

**Examples**:
- `ghcr.io/manyfold/web-frontend:x.y.z`
- `ghcr.io/manyfold/web-frontend:sha-a1b2c3d`
- `ghcr.io/manyfold/web-frontend:latest`

**Production Deployment Rule**: Always use immutable tags (semantic version or SHA) in production. Never use `latest` tag in production manifests.

**Rationale**: Immutable tags ensure reproducible deployments and enable safe rollbacks.

### 5. Maven Artifact Naming

**GroupId**: `dk.manyfold.{domain}`
**ArtifactId**: `{service-name}` or `{library-name}`
**Version**: Follow SemVer (see ADR-0003)

**Examples**:
```xml
<groupId>dk.manyfold.platform</groupId>
<artifactId>common-utils</artifactId>
<version>x.y.z</version>
```

```xml
<groupId>dk.manyfold.web</groupId>
<artifactId>frontend-service</artifactId>
<version>x.y.z</version>
```

**Rationale**: Maven reverse-domain naming convention with `dk.manyfold` as organization identifier.

### 6. Git Branch Naming

**Main Branches**:
- `main` - Production-ready code (lowercase)
- `develop` - Integration branch (if using GitFlow, lowercase)

**Feature Branches**:
**Format**: `feature/{ticket-id}-{short-description}`

**Examples**:
- `feature/MF-123-add-user-authentication` (lowercase description)
- `feature/MF-456-cilium-network-policies` (lowercase description)

**Bugfix Branches**:
**Format**: `bugfix/{ticket-id}-{short-description}`

**Examples**:
- `bugfix/MF-789-fix-login-redirect` (lowercase description)

**Hotfix Branches**:
**Format**: `hotfix/{version}-{description}`

**Examples**:
- `hotfix/x.y.z-critical-security-patch` (lowercase description)

**Release Branches** (if needed):
**Format**: `release/{version}`

**Examples**:
- `release/x.y.0`

**Note**: Branch names MUST use lowercase for all parts. Ticket IDs like "MF-123" are uppercase only because they reference external systems that mandate uppercase identifiers.

**Rationale**: Clear branch categorization enables automated CI/CD workflows and simplifies branch management.

### 7. API Versioning

**URL Path Versioning**: `/api/v{major}/resource`

**Examples**:
- `/api/v1/users` (lowercase)
- `/api/v2/orders` (lowercase)

**Rules**:
- Only major version in URL path
- Minor/patch versions maintain backward compatibility (no URL change)
- Deprecate old versions with 3-6 months notice
- Document breaking changes clearly
- **MUST** use lowercase for all path segments and resource names

**Rationale**: URL path versioning is explicit, simple, and widely supported by API clients. Lowercase ensures consistency and prevents case-sensitivity issues.

## Consequences

### Positive

- **Consistency**: Predictable naming across all resources
- **Discoverability**: Easy to find and identify resources
- **Automation-Friendly**: Clear patterns enable tool integration
- **Kubernetes Best Practices**: Aligns with official Kubernetes conventions
- **Troubleshooting**: Easier to correlate resources across tools (logs, metrics, traces)
- **Environment Portability**: Same manifests work across environments
- **Team Scalability**: Clear conventions reduce onboarding time

### Negative

- **Learning Curve**: Team must learn and remember conventions
- **Enforcement Overhead**: Requires validation to maintain consistency
- **Migration Effort**: Existing resources may need renaming
- **Verbosity**: Some names may be longer than minimal alternatives

### Mitigations

- Document standards in CLAUDE.md and developer onboarding
- Automated validation for Kubernetes manifests (OPA/Kyverno policy checks)
- Use tooling to enforce naming (Maven archetypes, Helm chart templates)
- Automated linters to enforce lowercase-first rule in CI/CD pipelines
- Create examples and templates for common scenarios
- IDE snippets for quick resource creation
- Pre-commit hooks to validate naming conventions

## Implementation Plan

1. **Phase 1**: Document standards (this ADR + CLAUDE.md update)
2. **Phase 2**: Create templates and examples
   - Kubernetes manifest templates
   - Maven POM templates
   - Helm chart value conventions
   - Branch naming examples
3. **Phase 3**: Implement validation tooling
   - Kubernetes manifest policy validation (OPA/Kyverno)
   - CI/CD checks for container image tags
   - Maven naming validation
4. **Phase 4**: Apply to existing resources (if any)

## Alternatives Considered

### Alternative: Environment in Resource Names

**Format**: `{service}-{environment}` (e.g., `frontend-prod`)

**Rejected Because**:
- Kubernetes namespaces already provide environment isolation
- Makes manifests environment-specific (harder to promote between environments)
- Reduces reusability of Helm charts and Kustomize bases
- Industry best practice uses namespaces for environment separation

### Alternative: Prefixless Custom Labels

Using labels without `manyfold.dk/` prefix.

**Rejected Because**:
- Kubernetes recommends domain-prefixed labels for custom fields
- Prevents collision with standard or third-party labels
- Clearer ownership and purpose

### Alternative: Separate Registries per Environment

Using different container registries for dev/test/prod.

**Rejected Because**:
- Adds operational complexity
- Image promotion between environments becomes harder
- Tag-based strategy with immutable production tags is simpler

## Notes

This ADR establishes foundational naming conventions for the Manyfold Platform. As the platform evolves, specific conventions may need refinement based on operational experience. Any changes to these standards should be documented in a new ADR or an amendment to this one.

**Review Triggers**:
- Introduction of new technology stack components
- Scaling beyond single developer (multi-team needs)
- Conflicts with third-party tool requirements
- Feedback from operational experience

## Amendment (2026-05-24, ADR-0033)

ADR-0033 adds the tenant dimension. Tenant namespaces are `<tenant>-<env>`
(tenant-first), carrying the mandatory label `manyfold.dk/tenant`, alongside the
existing `<env>-<domain>` convention for platform resources.
